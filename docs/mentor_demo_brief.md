# Mentor 展示掌控稿：交互 ROI 与受保护角度修正

## 1. 一句话介绍

这次新增的是一个交互式局部分析流程：用户只需在图像上点击一个参考点，程序会自动建立局部 ROI、判断点击位置、估计条纹倾角、在可信时修正角度、检测相邻黑色条纹，并把结果映射回原图坐标。

需要准确表述：当前不是“整张图完全自动寻找 ROI”，而是“点击一次后自动构造 ROI”。这保留了人的任务语义，同时把后续像素级处理全部自动化。

## 2. 展示时建议按这个顺序讲

1. 左侧选择项目图片或上传图片。
2. 在目标黑色条纹或其附近点击参考点。
3. 程序以点击点为中心自动建立 ROI；默认半宽、半高均为 250 px，所以正常 ROI 是 500 × 500 px。
4. 程序先运行未旋转 baseline，再搜索最佳角度。
5. 只有角度证据满足保护条件时，才在旋转后的 ROI 中重新检测；否则保留 baseline。
6. 如果旋转导致原本成功的检测失败，程序自动回退到未旋转结果。
7. 最后用逆仿射变换把中心线映射回原图，并保存可视化图片和 JSON 数据。

## 3. 完整数据流

```text
选择图片
  → 点击参考点 (x, y)
  → 自动裁取以点击点为中心的 ROI
  → 5×5 Gaussian blur
  → Otsu 自动阈值二值化
  → 3×25 竖向闭运算，连接白条纹的短缺口
  → 反相得到黑色区域 mask
  → 未旋转 baseline 检测
  → 在 -10° 到 +10° 范围评估角度
  → 角度保护判断
      ├─ 可信：旋转灰度 ROI，重新预处理和检测
      └─ 不可信：保留原始 ROI 检测
  → 点击语义选择相邻轨迹
  → 坐标映射回原图
  → 页面显示 + 保存 debug 图和 JSON
```

## 4. 自动 ROI 的具体实现

点击点是全局坐标 `(click_x_global, click_y_global)`。正常情况下：

```text
x0 = click_x - 250
x1 = click_x + 250
y0 = click_y - 250
y1 = click_y + 250
```

边界采用左闭右开，因此 ROI 宽高为 500 × 500 px。若靠近图像边缘，ROI 会安全裁切到图像范围内，并添加 `roi_clipped_*` 警告。为了避免边缘裁切影响旋转评分，裁切 ROI 不会实际应用角度修正。

页面显示图像可能被缩放到最大宽度 1100 px，但点击坐标会按 x/y 缩放比例映射回原始图像，不直接使用浏览器中的显示坐标。

## 5. 角度估计为什么有效

角度估计使用竖向闭运算后的二值图，而不是最终黑色 mask。

搜索范围是 `-10°` 到 `+10°`，步长 `0.25°`，共评估 81 个角度。对每个候选角度：

1. 将二值 ROI 旋转到该角度。
2. 去掉所有候选角度共有的保守边缘区域，避免旋转产生的黑色三角边影响评分。
3. 对每一列计算白色像素比例，得到 column profile。
4. 以 column profile 的标准差作为角度分数。

原理是：当条纹被校正为竖直时，白条纹会集中在固定列，列与列之间差异最大，所以 column profile 标准差较大；条纹倾斜时，白色像素会在多列间摊开，列差异变小。

角度符号代表“需要施加的修正角”。例如合成测试将竖直条纹旋转 `+4°`，算法会找到约 `-4°` 的最佳修正。

## 6. 为什么不是每次都旋转

最佳角度只是候选，必须同时通过以下保护条件：

| 条件 | 当前阈值/规则 |
| --- | ---: |
| 允许应用旋转 | `rotation_apply_enabled = true` |
| 最小绝对角度 | `0.5°` |
| 相对零度评分增益 | 至少 `10%` |
| 最佳峰与次佳峰分离度 | 至少 `5%` |
| 最佳角度不能在搜索边界 | 不能正好是 `-10°` 或 `+10°` |
| ROI 不能被图像边缘裁切 | 任意 `roi_clipped_*` 均不应用 |
| 旋转不能使检测退化 | baseline 成功而旋转失败时回退 |

评分公式：

```text
relative_score_gain = (best_score - zero_angle_score) / zero_angle_score
peak_separation = (best_score - second_score) / best_score
```

这里的设计重点是“有证据才修改检测空间”。角度估计始终会显示，但 `estimated angle` 和 `applied angle` 可能不同。

## 7. 相邻黑色条纹检测原理

1. 在黑色区域 mask 上逐行提取连续黑色 run。
2. 每个 run 计算宽度和中心位置；偶数宽度允许得到半像素中心，例如 `234.5`。
3. 按宽度、是否触边、与参考 x 的距离做初筛。
4. 对 run 中心沿 x 方向投票聚类，形成近似竖直的轨迹 seed。
5. 每条轨迹在每一行最多分配一个最近 run。
6. 使用中心中位数与宽度中位数过滤异常 run，避免黑洞、粘连等宽度异常污染中心线。
7. 轨迹至少要覆盖 ROI 高度的 50% 才算稳定。

如果点击的是稳定黑色条纹，程序将这条轨迹视为“被点击/排除的中心条纹”，再选择其左右最近的稳定黑色轨迹；如果点击的是白色区域，则直接选择参考线左右最近的稳定轨迹。

关键检测参数：

| 参数 | 当前值 |
| --- | ---: |
| 黑色条纹搜索半径 | ±120 px |
| run 最小宽度 | 3 px |
| run 最大宽度 | 120 px |
| 中心聚类容差 | 5 px |
| 最大宽度偏差比例 | 75% |
| 最小宽度容差 | 3 px |
| 最小有效行比例 | 50% |
| 拒绝接触 ROI 左右边界的 run | 是 |

## 10. 展示时可以主动承认的限制

- ROI 仍需要一次人工点击，目前没有整图自动定位目标区域。
- 角度只搜索 `[-10°, +10°]`；超过范围会落到边界并被保护机制拒绝。
- 角度分数假设 ROI 内的主要结构应接近竖直且具有重复列结构。
- 靠近图像边缘、ROI 被裁切时，为避免旋转伪影，不应用角度修正。
- 当前阈值是可配置的工程 baseline，还需要更多真实图像验证泛化能力。
- `distance_to_click_px` 和 `stripe_spacing_px` 是检测空间中的水平距离，不是任意方向的欧氏距离。

主动说明这些限制并不削弱项目，反而能表明算法边界、失败策略和后续验证路径是明确的。

## 11. Mentor 常见追问与回答

### 为什么不用 Hough Transform？

当前目标不仅是估角，还要处理断裂、噪声和宽度不均匀的条纹。列投影评分与现有逐行 run 检测能直接复用，参数少、结果可解释，而且符合当前项目保持简单 OpenCV baseline 的要求。Hough 可以作为未来对比方案，但目前没有必要增加复杂度。

### 为什么使用中位数而不是平均数？

中位数对局部黑洞、粘连和异常宽 run 更稳健。少量极端行不会显著拉偏整条轨迹中心和典型宽度。

### 为什么旋转二值图估角，却旋转灰度图做检测？

二值图能让角度评分更直接、更快；真正检测时旋转灰度 ROI，然后重新执行模糊、Otsu 和形态学处理，可以避免直接旋转旧 mask 把插值或边缘伪影固化到最终检测中。

### 为什么旋转中心是点击点？

点击点代表用户关心的参考位置。围绕它旋转可以保持参考点在 ROI 中的位置不变，降低旋转前后选择语义发生漂移的风险。

### 为什么最佳角度不一定被应用？

离散搜索总能产生一个数值最大值，即使图像实际上已经竖直或证据很弱。因此必须比较角度大小、相对零度增益、峰值独特性、边界情况和检测是否退化，避免为了“有结果”而过度修正。

### 如何知道结果可信？

查看 `valid_row_ratio` 和 `retention_ratio`。前者表示轨迹覆盖 ROI 高度的比例，后者表示分配到轨迹的 run 中有多少通过一致性过滤。本例左右两侧两项指标均为 100%。此外，页面和 JSON 会给出角度保护原因、warning 和 fallback。
